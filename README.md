# Agricultural LCA Models — New Datasets Pipeline

Automated pipeline that enriches and converts agricultural Life Cycle Assessment (LCA) datasets from the **DataX / EcoSpold2** format into ecoEditor-ready `.spold` files.

---

## Overview

The pipeline runs three models in sequence, each adding calculated exchanges to the dataset:

| Step | Module | What it does |
|------|--------|-------------|
| 1 | **OLCApest** | Redistributes pesticide emissions across four environmental compartments (air, soil, soil-forestry, water) using the OLCA mapping tool |
| 2 | **Multinutrient** | Splits multi-nutrient fertiliser exchanges (NPK blends) into individual N / P₂O₅ / K₂O rows using mass-based allocation factors |
| 3 | **Agri Diesel** | Adds diesel consumption rows for field operations (tillage, spraying, harvesting, etc.) using per-geography ecoinvent intensities |
| 4 | **Meta Model** | Enforces the activityName nomenclature and the house style of the `meta` sheet across the whole project. Proposes; nothing is saved until you approve it |
| — | **SPOLD Converter** | Writes EcoSpold2 XML (`.spold`) for import into ecoEditor. Not a step of its own: every step above rewrites the `.spold` of each workbook it saves, so `spold_output/` always matches the workbooks |

**Input formats accepted:**
- `.xlsx` — DataX format (ecoEditor export)
- `.spold` — EcoSpold2 file; automatically converted to DataX by the built-in reader before processing

Python's compiled caches all go to `.venv/pycache` (set by the runner, VS Code's Run
entries and its terminal), so no `__pycache__` folder appears among the code.

**Diesel intensities (Agri Diesel step 3):**  
Diesel intensities live in the `FO_DIESEL_INTENSITIES` table in `config_new_datasets.py`
— 104 rows giving kg diesel per hectare for 65 field operations across 151 geographies.
Geographies that share an identical intensity are collapsed onto one row with their codes
pipe-joined (`'CH|GLO'`), and the calculator expands them back into one entry per geography
at load time. The pipeline reads nothing else: no 87 MB Excel file, no pickle cache.

Only field operations with a **relevant** diesel input are listed. To qualify, the activity
must be measured per hectare and its diesel input must be machinery diesel in kg. That
excludes irrigation and water pumping (per m³ / MJ), agricultural freight transport (per
metric ton·km) and the `market for ...` activities — their diesel is real, but it is not
diesel per hectare of field work, so pairing it with a hectare amount would be meaningless.

The table is generated from the raw ecoinvent sources, which are needed **only** when
regenerating it after an ecoinvent release:
```
C:\python\Fuel Project\excel\exchanges (3.12, undef).xlsx   # diesel exchange amounts
C:\python\Fuel Project\excel\FO UND.xlsx                    # field-operation whitelist
```
```powershell
& $py agri_diesel_new_datasets\build_fo_diesel_table.py           # preview
& $py agri_diesel_new_datasets\build_fo_diesel_table.py --write   # patch the config
```
`--write` replaces everything between the `BEGIN/END GENERATED: FO_DIESEL_INTENSITIES`
markers in `config_new_datasets.py` and leaves the rest of the file untouched.

## Running the Pipeline

### With the graphical UI (recommended)

```powershell
& ".venv\Scripts\python.exe" run_pipeline.py
```

`run_pipeline.py` runs, in order: the meta model (prepare: start each working copy from the input and correct it), OLCApest, Multinutrient, Agri Diesel, the meta model again (corrections on what the models added, every checklist check, and the project's review workbook), and `verify_output.py`. The steps are a plain list at the top of the file — **comment out a line to leave that step out**. Without the prepare step the models start from `input datasets/`, exactly as `run_three_models.py` (the three models alone) does. The run ends by naming the review workbook to answer.

The UI lets you:
- Select a project folder under `input datasets/`
- Select one or more input files (`.xlsx` or `.spold`)
- Click **Import & Run Pipeline** to process all selected files in batch

### After correcting an output workbook by hand: `recheck.py`

```powershell
& .venv\Scripts\python.exe recheck.py            # the same chooser as run_pipeline.py
& .venv\Scripts\python.exe recheck.py --no-ui    # the project in the config
```

Or press **Re-check** next to **Run Pipeline** in `run_pipeline.py`'s chooser (pick the project and its datasets first) -- the review window opens afterwards, as after a full run. Re-runs the meta model's checks and review, writes each `.spold` and verifies -- on the workbooks in `output/<project>/` as you left them, recalculating nothing. The calculators always start from `input datasets/`, so a full run would replace a hand edit with the input's value: a correction meant to last belongs in the input dataset, or as an answer in the review's `Action_list`, followed by `run_pipeline.py`. A full run records what each dataset was calculated from (`calculation_fingerprints.json`: the yield, the inputs bought, the land); `recheck.py` names the datasets whose edit touched any of that, since their emissions and diesel are then out of date.

- **Properties: Master Data is the standard.** Wherever Master Data defines a property of a flow -- an input or the dataset's own product -- its value is used: a missing one added, a different one replaced, each change listed with its old and new value (`Corrections`; `apply = no` keeps the dataset's values). The price of the dataset's own products is the exception: it is allocation data, varying by variety and region, so Master Data only supplies it when missing. The ecoinvent export defaults then fill what Master Data does not define. A price or missing properties typed in `your_fix` set those properties: `0.63` (EUR2005) or `0.70 USD2022`; `dry mass = 1; wet mass = 6.667`.
- **Correcting many datasets at once, in the split Excels** (`split_edits.py`): every run ends by rebuilding `crop_datasets_new/<project>_part_N.xlsx` from the final datasets and stamps each part with a fingerprint of itself as built (in its document properties) -- no copy is kept, the folder holds only the part files. Edit a part file -- Find & Replace across every dataset, a column filled down, a row deleted or added -- save it, and press **Re-check** (or run `recheck.py`): the parts that no longer match their fingerprint are compared with a fresh build from the datasets (in a temporary folder), and the differences are exactly your edits, and each is applied to the dataset workbook that owns the row (by its activityName), listed in Changes Applied, a deleted row in the Deleted sheet. Rows are matched by content, so rows moving around is fine; a row the dataset no longer has as it was is reported and left alone. Then the checks run on the corrected datasets and the splits are rebuilt. If the datasets themselves were changed since the part was built, the edits cannot be told apart from those changes and are not applied; the part is kept in `unapplied_edits/` rather than lost. Edit cells and rows, not the columns. As with any edit of the outputs, a full pipeline run starts again from the input -- a correction meant to last goes into the input, or as an answer in the review.
- **MD** in the review checklist is Master Data; the review spells it out.

### Without the UI (uses current config defaults)

```powershell
& ".venv\Scripts\python.exe" run_pipeline.py --no-ui
```

### Batch mode (programmatic)

Each pipeline script accepts `--batch` with a JSON list of `[project, filename]` pairs:

```powershell
$py = ".venv\Scripts\python.exe"
$batch = '[["Olive,TN","olive_datasets_TN.spold"],["ILCIDAF project full","orange_production__integrated__irrigated__fresh_grade__south.xlsx"]]'
& $py OLCApest_emissions_calculation\read_pesticide_data_new.py --batch $batch
& $py multinutrient_new_datasets\multinutrient_calculator_new.py --batch $batch
& $py agri_diesel_new_datasets\agri_diesel_calculator_new.py --batch $batch
& $py spold_output_new_datasets\spold_converter_new.py --batch $batch   # optional: each step above already wrote the .spold
```

## Notes

- **Multi-activity `.spold` files** are supported: each activity in the spold becomes a separate row in the DataX output and a separate `.spold` output file.
- **Geography fallback** for diesel intensities: if the crop geography has no direct entry in the intensity table, the fallback order is `GLO → RoW`, then the median across all geographies for that field operation. Manual overrides are stored in `config/models/fo_geography_map.csv`.
- **Diesel statement moves to the diesel row**: when the per-hectare figure is read from an FO exchange comment, it is written into the generated `diesel used in, ...` row's comment ("The diesel consumption of this field operation is 23 kg per hectare.") and the diesel wording is removed from the FO comment. Only the diesel clause goes — the yield-scaling statement, which explains the FO amount, stays. Re-running the step over its own output is safe: the figure is read back from the diesel row, since the FO comment no longer carries it.
- **Application count in the FO comment**: the pass count the FO amount was built from is stated as `The quantity corresponds to 3 applications.` (singular at 1). It reports the count the calculator already settled on — the comment figure when the dataset gives one, otherwise the rounded value — and is never re-rounded. On a re-run this sentence is authoritative: it is read back as-is and replaced in place, never summed with an older `N treatments` mention left elsewhere in the comment or duplicated.
- **Meta model — universal, profile-driven**: nothing about crops, regions, ISIC codes or constant values is hardcoded, so the model works on any project. `meta_spec.py` holds only the UNIVERSAL rules: the canonical text form, the locked yield line, and how an activityName is normalised (lowercase, `', '` separated, single spaces — the only grounds on which a dataset is ever renamed). Everything project-specific is induced into `meta_profile.py` by `build_meta_spec.py`: the crop families (simply the first segment of each activityName, whatever it is), how many axes each family's names carry and whether the last is optional, the vocabulary of each axis, the ISIC per family, the constant column values, and the house wording of each prose column. Values are taken by MAJORITY, so the minority reads as the deviation. An axis whose values are nearly all distinct (the grape variety) is recognised as an open identifier and new values there are not flagged.
  ```powershell
  & $py meta_model/build_meta_spec.py --project "My project" --write   # profile a project
  & $py meta_model/meta_model_new.py  --project "My project" --report-only
  ```
  Run the builder once per project, or point it at a reviewed reference project whose style later projects should follow. A crop family the profile has never seen still parses and still gets every universal check — it is reported as INFO, not failed. Without any profile only the universal rules apply, and the model says so. Every run writes the project's review workbook, `output/<project>/<project> review.xlsx` (see below).
- **Yield line (LOCKED FORMAT)**: `generalComment` must state the crop yield as exactly `Yield: [26299.94] kg/ha` — square brackets, the short unit `kg/ha`, and the number with a period separator, no thousands separator, and two decimals unless the figure is whole (`Yield: [9000] kg/ha`). This is a locked rule, not a style preference: the Agri Diesel step reads the figure back out of the prose to round field-operation passes, so its shape is part of the data contract. `meta_spec.format_yield()` normalises messy input automatically — comma decimals (`14000,50`), European thousands (`17.089,84`), scientific notation (`2.27E+03`), the long unit (`kg per hectare`) and a doubled decimal point (`2734.63.00`). The figure is also found whatever the sentence around it says — `Yield of the dataset = 1400.35 kg/ha`, `Annual production-average yield is 2249.9 kg/ha` — and the old declaration is REPLACED by the locked line, keeping any clause that follows it (`..., calculated as a weighted average of the regional yields.`). Where the figure sits buried mid-sentence the rewrite is proposed rather than applied, because only a human can judge whether the sentence still reads. A comment with no readable figure is **BLOCKING**: the yield cannot be invented and has to be supplied.
- **Uniform nomenclature / metadata checks** (`check_metadata_nomenclature.py`, ported from the .spold review skill): run against EVERY dataset so the two historically under-checked categories can never be silently skipped. Emits a PASS finding when clean, so each checklist row is populated either way. Covers ActivityName and Geography as two SEPARATE findings (axis presence, `at farm`/`at plant`, `region` wording, geography leaking into the name, Geography Comment populated); field presence across the seven metadata fields; the locked yield line; short-form citations (INFO); and CROSS-CONTAMINATION — another crop's name in a field that should only mention this dataset's own crop. Severities are BLOCKING / ACCEPTABLE_FOR_NOW / WARNING / INFO / PASS. Nomenclature axis problems are reported, never auto-renamed — only case and spacing are normalised automatically.
- **Generating a missing comment**: `generate_metadata.py` is the template filler — a fixed sentence skeleton per field, where only the substituted values change. It also holds the locked `format_yield()`; `meta_spec.format_yield()` parses messy input (brackets, trailing unit, doubled decimal point, scientific notation) and hands the number to it, so the pipeline and the review skill emit byte-identical yield lines. When a prose column is blank the model fills it, but only where every input can be derived from the dataset itself. It reads those inputs by axis MEANING rather than position: the profile labels each activityName axis from the vocabulary it holds (`conventional/organic/integrated` is a production system anywhere), so `grape production, asti, conventional, irrigated, south` yields crop/system/water regime/region on any project. `geographyComment` and `timePeriodComment` are generated this way; `generalComment` deliberately is not, because its template needs the yield and the yield lives in the generalComment — that stays BLOCKING for a human. Nothing is invented: a column whose inputs cannot be derived is reported and left blank.
- **Comments built from facts, as automatically as possible** (`meta_model/meta_facts.py`): every fact a comment states is established once and every comment is built from it, so a period, a source or a crop name cannot be written one way in one field and another in the next. A fact comes from the provider's optional `facts` sheet in the input dataset (`dataset_input_template.xlsx`: data source, its reference, farms sampled, extrapolations, region detail, share of national production, PV years) and, where the provider gave none, is derived from the dataset itself -- how the data were obtained from the technology / time-period comments, the sources from the citations there, the PV years from `PV_comment`. Blank `samplingProcedure`, `timePeriodComment`, `geographyComment` and `extrapolations` are filled from them; an existing text is never overwritten (where it departs from the house wording the built text is proposed). The review's `Facts` sheet lists every fact used and where it came from, so a wrong one is corrected at its source. The same module checks the fields against each other and reports, never rewrites: the water regime in the name against the irrigation input and the land-use flows, organic production against synthetic nitrogen, the PV years against the dataset period, and another country named in the comments than the dataset's geography.
- **One review workbook per project** (`output/<project>/<project> review.xlsx`, written by `review_workbook.py`): it replaces the old report, corrections sheet and fix sheet, in the format of the team's two review skills (checkdataset, livestock-ecoinvent-check). Sheets: `Verdict` (per-dataset status, what is common to all datasets, must-fix, decisions, resolved) · `Activities overview` (D1..Dn labels, counts per severity) · `Action_list` · `Corrections` · `Checklist status` (every row of the internal review checklist × dataset: OK / CORRECTED / FAIL / VERIFY, or `-` where the model does not check that row yet) · `Changes Applied` (append-only log) · `All findings`. **Each distinct error is one row** — same field, same issue, same current value — listing every dataset it affects, with **one `your_fix` answer that is applied to all of them**. Only errors whose answer depends on the dataset's own figures (a missing yield, dates vs period, an allocation factor) get one answer line per dataset (`12-1`, `12-2`, ...). `Corrections` groups an identical before → after the same way: one `apply = no` rejects it in every dataset. Severity follows the skills' scale: BLOCKING → Critical, a finding offering choices → Decision, ACCEPTABLE_FOR_NOW → Medium, an unfixed WARNING → High, INFO → Verify. The first run migrates the old files: typed answers and the applied_log history are carried over, then the old files are removed.
- **The review skills' checks, on every run** (`meta_model/skill_checks.py`): the per-exchange checks of the checkdataset and livestock-ecoinvent-check skills run inside the meta model, so the review workbook answers their checklist rows for every dataset: uncertainty and pedigree present and valid (76-78 / agri 17 — the DQG formula itself is applied by the converter); the dataset's own products carry the 6 mandatory properties and a price (103-109 / agri 24, agri 26) and satisfy the property equations (agri 25); units and property values against Master Data (96 / agri 20, 24 — from `config/master_data/master_data_flow_index.json`, built by `build_master_data_index.py` from the MasterData workbook named in the config); duplicated flows, template text such as `leave empty` (emptied), formulas using undefined variables, property rows that join no exchange; agricultural air emissions outside non-urban air (agri 18, one decision for every dataset); and for livestock datasets nitrate to ground water, herd structure (culled cow/bull, standalone bull) and product names that link into the ecoinvent markets. Each check is tested both ways in `tests/test_skill_checks.py`.
- **What the database import will reject** (`verify_output.py`, the last step of `run_pipeline.py`): every exchange in the `.spold` files whose flow id or subcompartment id is not in Master Data is listed under `[import]` — a name the converter could not match, so it made an id up, which fails the import's foreign keys (`v3_valid_elementary_exchange`, `v3_valid_subcompartment`). Read from the files themselves, against the converter's own lookups, so it shows what fails now. Two causes the meta model now repairs itself: a product entered as a resource (`pesticide, unspecified` under FromEnvironment goes to FromTechnosphere, mirroring the elementary flow entered as a product), and a row with no group (read from its compartment: an emission, or a resource for `natural resource`).
- **Every correction stays reviewable, however many runs** (the `Corrections` sheet of the review workbook): the pipeline starts each dataset afresh from its input and makes the same corrections on every run, and its final pass then finds nothing left to correct. A hidden corrections register keeps every correction ever made — metadata cells, the automatic flow fixes (renamed flows, groups, compartments, placements, geography, prices, properties) and your answers — one entry per dataset and field, with when it was first and last applied. The `Corrections` sheet is drawn from it, the same change across datasets on one row. Set `apply` to `no` and that correction is skipped on every later run, by the pipeline and the review window alike, and stays listed as `rejected -- not applied` until you set it back to `yes`. Changes Applied records a change when it is new or its value changes, not again on every run. The review window's Corrections tab shows the whole register for the selected datasets.
- **Fixing what the model won't decide** (the `Action_list` sheet): every BLOCKING and ACCEPTABLE_FOR_NOW finding is listed with the current value, a `how_to_fix` hint, and an empty **`your_fix`** column. Type the correction there and re-run — the answers are applied before validation, so the finding they resolve disappears rather than being reported again. Typed answers are keyed to the finding and preserved across runs; the sheet is rebuilt around them, never over them. What `your_fix` means depends on the finding: a yield takes just the number (`8604,16` or `8604.16`, written into `generalComment` in the locked format), an `activityName` takes the full corrected name (renamed here and in every sheet that carries it), and any other column takes its replacement text. A value that cannot be applied is reported back as BLOCKING rather than silently dropped. The console also prints the BLOCKING findings grouped by issue at the end of every run.
- **includedActivitiesStart (STANDARD OPENING)**: the field always opens `This activity starts with ...`, naming what prepares the current cultivation — or `This activity starts after ...` where the boundary opens at a point in time. The equivalent `This activity begins with/after` is rewritten to the standard automatically, leaving the rest of the sentence untouched; any other opening is **BLOCKING**, because rewording someone's description is not mechanical. A worked example of the full standard (opening, then inputs, then the activities covered) is kept in `meta_spec.INCLUDED_START_EXAMPLE` and quoted in the fix sheet's `note` column.
- **Nothing is saved without your say-so**: a plain run PROPOSES. It computes every correction and writes it to the `Corrections` sheet of the review workbook — one row per distinct change with the `before` text, the `after` text, what caused it, and an `apply` column prefilled `yes` — and changes no dataset file. Set `apply` to `no` on anything you reject, then re-run with `--commit` to save the rest. Your `no` is sticky: the sheet is rebuilt around your decisions, and a rejected correction stays proposed-but-skipped on every later run instead of quietly reappearing. Approval is per changed CELL, not per rule, because several rules can touch one cell (a yield fix and a whitespace tidy both land in `generalComment`) and what you are judging is the resulting text. Every committed change is appended, with a timestamp, to the `Changes Applied` sheet — an append-only record of what was altered and when.
  ```powershell
  & $py meta_model/meta_model_new.py                                   # file chooser
  & $py meta_model/meta_model_new.py --no-ui                            # propose, all projects
  & $py meta_model/meta_model_new.py --project "My project"             # propose, one project
  & $py meta_model/meta_model_new.py --project "My project" --commit    # save approved
  & $py meta_model/meta_model_new.py --project "My project" --apply-all # skip review
  ```
  `--commit` refuses to run before anything has been proposed, so a first commit cannot save 549 unseen edits. The pipeline step proposes too: it no longer rewrites datasets on its own — switch it to `--apply-all` in `PIPELINE` if you want unattended normalisation.
- **One run, every project**: nothing about the meta model is per-project any more. A plain run covers **every** project under `output/`, and writes one review workbook per project into `output/<project>/` — one folder holding them all, with a folder per project inside, so the dataset folders stay datasets-only. Every row names the `project` it came from, and each key is `project||dataset|column`, so two projects may hold a dataset of the same name without confusion. `--project "X"` narrows a run when you want that; `--batch` (the pipeline) narrows to the datasets it was given. `meta_profile.py` likewise holds a profile per project keyed by name, so profiling a new one leaves the others intact and a single run can judge them all — an unprofiled project still gets every universal check and is listed as `NOT profiled`. A workbook with no `meta` sheet is an intermediate, not a dataset: it is skipped as INFO rather than failed.
- **The same input UI as the three models**: run `meta_model_new.py` with no arguments and it opens `project_input_ui` exactly as `run_pipeline.py` does — same title, same Project Name box, same Load Existing Project list, same Files box, same buttons. One input UI for the whole project, not a variant. Your choice is handed to the review window, which opens already scanned on those datasets. There is one input UI in the project, not two that drift apart; the pipeline's own wording is unchanged. Your choice is handed straight to the review window, which opens already scanned on those datasets: tick what to save, untick what you reject, press Save. `--no-ui` runs it headless, and any flag (`--project`, `--commit`, `--batch`, ...) is taken as an explicit instruction and never opens a window. The review window writes the same review workbook the command line does, so the two ways in never disagree.
- **Minor tidy-ups are accepted, not reported**: whitespace and a missing final stop carry no meaning and there is nothing to decide about them, so they are applied silently — kept out of the corrections sheet, out of the fix sheet and out of the report, and summed in one console line (`339 minor tidy-up(s) accepted automatically`). A cell is only treated as minor when EVERY reason for changing it is cosmetic: a `generalComment` fixed for whitespace *and* a wrong yield still needs your decision.
- **A BLOCKING finding shows its proposed correction, beside the decision**: where a correction can be derived the model suggests one and puts it in the `proposed_fix` column of the fix sheet, next to the finding waiting on you. Type `yes` in `your_fix` to take it, or type your own text to use that instead. In the review window the row is highlighted, `Proposed?` reads yes, the suggestion is shown in full, and **Use proposed** takes it. Cross-contamination is the clear case — in a clementine dataset, `oranges production` → `clementines production` is mechanical. A finding with nothing derivable (a missing yield, a naming axis simply absent from the data) shows no proposal and waits for your value.
- **The Corrections sheet is the important corrections, applied automatically**: the locked yield line, the standard `This activity starts with` opening, the crop family's ISIC. All start ticked — untick anything you reject. Cosmetic tidy-ups are not listed (see above), and nothing needing judgement is in there either: that lives with the BLOCKING findings.
- **An empty metadata field is generated and proposed**: `samplingProcedure` is empty in all 129 datasets, so the model builds it from what the dataset already establishes — crop and cultivation system from the activity name, region where the name carries one, the kind of source read back out of `technologyComment` (`literature data` / `data collected on field` / `statistical sources`), and the period from `startDate`/`endDate`:
  ```
  Data on conventional grape cultivation in the south are based on literature data.
  The figures cover the period 2015 - 2020 and represent an average over that period.
  ```
  It arrives as a proposal in `proposed_fix`, never written on its own — type `yes` to take it. A missing input drops its clause rather than being guessed at, and compass regions take an article (`in the south`, not `in south`) so generated prose reads like the hand-written text beside it. `geographyComment` and `timePeriodComment` are generated the same way; `generalComment` still is not, because its template needs the yield and the yield lives in it.
- **A saved correction reaches the Excel splits and the .spold files too**: both are BUILT FROM the dataset workbooks, so a correction that stopped at the workbook would leave them contradicting it — the pipeline writes the splits in step 3, before the meta model runs at all. On every commit the affected `.spold` files are regenerated and the project's `crop_datasets_new/` part files are rebuilt from the corrected datasets. They are regenerated, never patched: a derived file edited in place drifts from its source. `--no-downstream` skips it. Nothing is rebuilt when nothing was saved.
- **The pipeline continues into the meta model**: the meta model runs as step 4 and PROPOSES — it saves nothing on its own. (Historical: an earlier runner carried straight on into the review window. `run_pipeline.py` now ends by naming the project's review workbook instead.)
  ```
  ================================================================================
  META MODEL -- review what it wants to change
  ================================================================================
    196 important correction(s) proposed, 112 finding(s) need your decision.
    Nothing has been saved yet. Opening the review window...
  ```
  A scripted `--no-ui` pipeline run stays headless but still reports what is waiting and the exact command to review and commit it — ending a run in silence is how a review queue gets forgotten. Approving there rebuilds the `.spold` files and split Excels, so the corrections reach every output.
- **Pesticide emissions are stated one way, everywhere**: how they were calculated is not a per-dataset choice — this pipeline computes them with OLCA-Pest in step 1 — so `modellingAndValidation_extrapolations` always carries exactly:
  ```
  The emissions due to pesticides use are calculated according to the OLCA-Pest model (Nemecek et al. 2022).
  ```
  Any other wording of it is replaced (the datasets variously credited `"Zampori and Pant, 2019"`, `"Zampori et al, 2019"` and three different phrasings — 116 datasets), and a column that never mentioned it gains the sentence (13 datasets). Only sentences about pesticide EMISSIONS are touched: one that mentions pesticides for another reason — where the quantities came from, what the data represent, packaging end-of-life — says nothing about the calculation and is left exactly as it is. The **fertiliser** emissions sentence is likewise untouched.
- **OLCApest cache**: the tool Excel (`OLCApest mapping tool_AG_updated.xlsx`) is pickle-cached after the first load; delete the `.pkl` file in `config/models/` to force a reload.
